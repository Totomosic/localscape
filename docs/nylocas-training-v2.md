## Reproduction and measurement

`tools/simulate-nylocas.py` snapshots canonical Java sources before each batch and compiles that immutable copy using `nylo.policySource`. Use a fresh output directory for each invocation. `--policy-source` selects an alternate source tree for controlled comparisons without mutating the working policies. Reports retain policy hashes and fixture conditions. New runs also archive adapter sources: replaying an old Java model may require its matching adapter, since typed observation fields can evolve.

Stalls use the last successfully spawned wave. Existing CSV `wave_29_stalls` retains its historical incoming-wave name and therefore means a **wave-28 stall** in the brief. The new `stalls_by_last_spawned_wave` column holds counters for waves 0–30. Pre-cap covers last-spawned 1–19. The post-cap consistency metric checks waves 21–27 separately from the explicitly allowed two or three wave-28 retries. Failed rooms never count as meeting consistency goals; their deaths/timeouts remain visible.

`--prepot` is an explicit separate fixture condition. It consumes supported super attack, super strength, super defence, ranging and magic potions through ordinary held-item handlers before the timed room. The existing magic potion grants only +4; it does not reproduce the qualifying replay's initial 112 magic. Initial 118 melee and 112 ranged/magic are recorded in the pinned `0c25e1` replay, so unboosted 99-current-stat runs and pre-potted runs must not be mixed without labeling them.

## Live-world profile correction

The pre-existing server `LoginScript` maintains **118 attack/strength/defence and 112 ranged/magic** for every processed player; this predates the bot work (upstream commit `635b7e92`). Live bots receive the same behavior as human players. Earlier simulation profiles omitted that script and `StatRegenScript`, so their potion-only 103 Magic results are valid controls but do not establish full live-world parity. They also did not exercise native passive regeneration/boost decay. The prior live documentation's claim that magic stayed at the potion's 103 was incorrect.

`--server-boosts` explicitly loads those existing production scripts, with no new stat-grant logic in the controller. A regression at the shared batch script-list seam failed with expected 112 versus actual 99 without `LoginScript`; loading it passed initial boost, complete magic-drain recovery and recurring-decay checks. Ordinary dose consumption remains separately verified. New CSVs retain final Magic levels for both roles; metadata separates this profile from all older controls. All 46 vetted mage recordings expose 112 Magic at initial, wave-31 and last-Eye checkpoints; the other role's Magic cannot be inferred from those remote-player packets.

Under this live profile, seeds 31–130 completed 100/100 at **338.80 ticks / 3:23.28**, pre-cap 4.54. Prioritizing only fresh cleanup magic splits that ranger is permanently NULL on changed the mean to **338.40**, with eight faster, 90 tied and two slower rooms; that narrow rule is adopted. The isolated south-11-before-west-11 variant matches all 46 human sequences but measured 339.24 ticks and 4.90 pre-cap stalls, so it is not adopted.
